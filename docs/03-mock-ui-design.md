# モック UI 設計(テーマ駆動レンダリング)

2026-08-21 時点のモック UI の設計方針と、`mock/` ディレクトリの実装の対応関係をまとめる。

## dpi が未確定でも設計できる理由

dp は「Android が実装時に px を密度で割るための単位」でしかない。
モック設計に必要な物理量はすべて確定している。

- パネルの px:カバー 1248×1972、メイン 2448×1848(スクリーンショットで確認済み)
- パネルの物理寸法:カバー約74×117mm、メイン約154×116mm(公開スペック)

したがってモックは **px を一次単位**として設計する。
dpi(densityDpi)が効くのは実装フェーズの次の3点だけで、いずれも今の設計を破綻させない。

1. タッチターゲット下限(48dp)。最悪ケースの 3.0x でも 144px であり、6列グリッドのセル幅(約195px)に収まる。
2. OS の Size Class 判定。仕様書 01 のとおり自前の実寸判定にするので依存しない。
3. テキストの自動スケール。実装時に sp を使うか px 固定にするかを選ぶだけ。

## 確定した要件(ユーザー確認済み)

- One UI 標準はカバー4列が上限。現在の6列は Good Lock による拡張で、**このサイズ感(セルピッチ208px)を維持する**。
- 見た目は普通のホーム画面である必要はなく、**SF・ゲームに登場するモバイル端末のような雰囲気でよい**。
- **テーマ定義ファイルを読んで自由にレイアウトできる**構造にする。

## ゾーンモデル

doc 02 の発見をそのまま構造化した。

```
カバー画面(閉)                メイン画面(開)
┌──────────────┐   ┌──────────────┬─┬──────────────┐
│ status       │   │ status(全幅)                  │
│ widgets      │   ├──────────────┼─┼──────────────┤
│ folders      │   │ EXTENSION    │H│ ANCHOR       │
│ apps 6col    │   │ (開いたとき  │I│ (カバーの    │
│ search       │   │  だけの拡張  │N│  widgets+    │
│ dock         │   │  パネル)     │G│  folders+    │
└──────────────┘   │              │E│  apps を同期)│
                   ├──────────────┴─┴──────────────┤
                   │ search + dock(中央・共有)     │
                   └───────────────────────────────┘
```

- **ANCHOR ゾーン**:カバーのホーム面(widgets / folders / apps)がそのまま出る。実装ではデータソースを共有するだけで同期が成立する(モックでも `coverContent()` を両画面から呼んでいる)。
- **EXTENSION ゾーン**:開いたときだけ存在する面。カレンダー・ヘルスケア・乗換など「広げて見るもの」を置く。
- **HINGE**:物理ヒンジ位置の可視化(装飾。テーマで消せる)。
- search / dock はメインでは全幅下部の共有レールになる(One UI の実挙動と一致)。
- アンカーの左右はテーマの `screens.main.anchorSide` で選べる(利き手対応)。

## テーマ定義ファイル

`mock/themes/*.json`。スキーマの要点:

| キー | 内容 |
| --- | --- |
| `palette` | surface / line / accent / accent2 / warn / text / textDim |
| `wallpaper` | CSS background 値(グラデーション等) |
| `typography` | ui フォントと mono フォント |
| `decor` | cornerBrackets / scanlines / gridDots / zoneHeaders / hingeMarker の on/off |
| `icon` | shape(squircle/circle/hex)、size、labels、monochrome |
| `moduleRadius` | ウィジェット等の角丸 px |
| `screens.cover.grid` | 列数とセルピッチ(6列・208px) |
| `screens.cover.widgets` | ウィジェットスロット配列 `{widget, w, h}`(6列グリッド上のスパン) |
| `screens.main.anchorSide` | `left` / `right` |
| `screens.main.extensionWidgets` | 拡張パネルのウィジェットスロット配列 |

同梱テーマ:

- **amber-terminal**:SF端末風。暗い機体色+琥珀の計器+青緑のサブ表示、コーナーブラケット、走査線、ゾーンヘッダ(`EXT.PANEL // UNFOLD+` 等)、ヒンジマーカー。
- **paper-white**:対比用ミニマル。装飾ゼロ・円形アイコン・明朝。同じレイアウト定義が別世界観になることの証明。

## モックの使い方

```bash
cd mock && python3 -m http.server 8814
# http://localhost:8814/index.html を開く
# テーマはヘッダのボタン、または ?theme=paper-white で切替
```

- 2画面を実解像度 px で組み、CSS `zoom` で縮小表示(30/38/50%)。
- アプリ・フォルダ・ウィジェットの中身は実機スクリーンショット(2026-08-21)を模したダミーデータ(`renderer.js` の `DATA`)。

## 実装に持ち越す設計判断

- テーマ JSON はそのまま Kotlin 実装の設定フォーマットの叩き台になる(kotlinx.serialization で読む想定)。
- ウィジェットスロットの `{widget, w, h}` グリッドは AppWidgetHost のセル割当てにそのまま対応させる。
- アンカー同期は「カバー用レイアウトデータを単一ソースにして両画面が参照する」実装にする(モックと同じ構造)。
