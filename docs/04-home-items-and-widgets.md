# ホーム画面の構成要素とウィジェットの設計

ホーム画面に置くものをどう表現し、どう組み合わせるかを決める。
方針として、ホームに表示するもの(時計、グラフ、天気など)はすべて自作のウィジェットとして個別に作り、通常の Android ウィジェットも同じ場所に置けるようにする。
あわせて、アプリのフォルダ化とグループ化、アプリドロワー、ドックの扱いを決める。
docs/03 のゾーンモデル(カバー面をメイン画面の片側にアンカーし、反対側を拡張パネルにする)は前提としてそのまま使う。

## ホームに置けるものはすべて「アイテム」として扱う

ホーム画面に表示できるものは、アプリ、フォルダ、自作ウィジェット、Android ウィジェットの4種類ある。
これらは見た目も振る舞いも違うが、「グリッド上の矩形を占め、タップや長押しに反応し、永続化される」という点では同じである。
そこで、この共通部分を **アイテム** と呼び、4種類をその下位型として定義する。

- **AppItem**：アプリ起動アクティビティへの参照(コンポーネント名とユーザー)。
- **FolderItem**：アイテムの集合。中身は AppItem に限る。
- **NativeWidgetItem**：自作ウィジェットのインスタンス。ウィジェット種別の ID と、その種別固有の設定を持つ。
- **AppWidgetItem**：Android の AppWidget のインスタンス。プロバイダのコンポーネント名と `appWidgetId` を持つ。

すべてのアイテムは **配置**(どのゾーンの、何列何行目に、何列何行分)を持つ。
配置をアイテム側に持たせるのは、レイアウトエンジン、編集操作(移動、リサイズ、削除)、永続化がアイテムの種類を知らずに済むようにするためである。
種類ごとの違いは、描画とタップ時の動作の2箇所に閉じ込める。

実装上は Kotlin の sealed interface にする。
種類による分岐は `when` で網羅され、種類を増やしたときにコンパイラが分岐漏れを指摘する。
フォルダは中にアイテムを含むので Composite パターンにあたるが、入れ子はフォルダ1段までに制限する。

## 自作ウィジェットは仕様、データ源、描画の三つに分ける

自作ウィジェットは「時計」「バッテリー計器」のような種別ごとに作る。
このとき、一つの種別を一つのクラスにまとめると、見た目を変えたいだけでもデータ取得のコードに触ることになる。
テーマで見た目を差し替えたいという要件(docs/03)があるので、種別を三つの部品に分ける。

- **WidgetSpec**：種別の ID、表示名、許容するスパン(最小と最大の列数と行数)、インスタンス設定のスキーマ。
- **WidgetDataSource**：データを `Flow` で流す。時刻、バッテリー、天気 API、起動ログなど、種別ごとの取得手段はここに閉じる。
- **WidgetRenderer**：データを受け取って描く Composable。同じ種別に複数のレンダラを登録でき、テーマがどれを使うかを選ぶ。

たとえば天気なら、データ源は一つで、レンダラは「計器風」と「数字だけ」の二つを持てる。
テーマの切り替えは、レンダラの選択と配色の差し替えで成立する。

種別は **WidgetRegistry** に登録し、レイアウトファイルとテーマファイルからは ID で参照する。
種別を追加する作業は、この三つを書いてレジストリに登録するだけにする。

最初に作る種別は、状態表示に寄せたものにする。

- 時計と日付
- バッテリーと通信状態の計器(モックの `83% BATT` 相当)
- アプリ起動頻度のグラフ(後述の起動ログを使う)
- 折りたたみメトリクス(現在の v0.1 の帯をウィジェットに移す。実機の実測用)

天気や乗換案内など外部 API を使う種別は、認証情報の扱いを決めてからにする。

## Android ウィジェットは同じアイテムとして載せる

通常の AppWidget は、`AppWidgetHost` が生成する `AppWidgetHostView` を Compose の `AndroidView` で包んで描く。
AppWidgetItem は NativeWidgetItem と同じ配置情報を持ち、描画だけをホストに委譲する。
レイアウトエンジンから見れば両者は区別されない。

AppWidget には自作ウィジェットにない制約がいくつかある。

- インスタンスの生成に `appWidgetId` の割り当てとバインド(必要なら `ACTION_APPWIDGET_BIND` の許可ダイアログ)が要る。設定アクティビティを持つプロバイダでは、その起動も要る。
- ホストは `startListening` と `stopListening` をアクティビティのライフサイクルに合わせて呼ぶ。
- セルの実寸を `updateAppWidgetSize` で伝える。カバーとメインでセルピッチが違う(docs/02)ので、面ごとに伝え直す。
- Android 17 のウィジェット密度スケーリング(docs/01)がカバーとメインの ppi 差にどう効くかは実機で見るまでわからない。

もう一点、アンカー同期との相性が未確定である。
カバー面のアイテムをメイン画面のアンカーゾーンにもそのまま出すので、同じ `appWidgetId` のビューを二つの面で使い回すことになる。
同時に表示されることはない(カバーとメインは同時に点灯しない)ので一つのホストビューを付け替えれば足りるはずだが、実機で確かめる。

## フォルダとグループの区別

アプリをまとめる手段は、手動で作る **フォルダ** と、規則で中身が決まる **スマートフォルダ** の二つにする。
どちらも FolderItem であり、中身の決まり方だけが違う。

- 手動：ユーザーが入れたアプリの並び。
- 最近起動：起動ログの新しい順。
- よく使う：起動ログの回数順。
- カテゴリ：`ApplicationInfo.category`(音楽、SNS、ゲームなど)で自動分類。

起動の回数と時刻は `UsageStatsManager` から取る。
ランチャー自身の起動記録で代用する案もあったが、通知やウィジェットからの起動を取りこぼすので、使用状況アクセスの権限をユーザーに許可してもらう方を選んだ(2026-09-03 決定)。
権限が未許可のあいだは、規則つきフォルダを空にせず、許可画面への導線を中に出す。

「常駐させたいアプリ」のために別の概念は作らない。
ドックとホームの手動配置がその役割を担う。

フォルダを開いたときの表現は、両画面ともポップアップにする(docs/03 の未決事項)。
その場で展開する方式はグリッドの再配置を伴い、編集モードのドラッグと干渉する。
ポップアップの形と装飾はテーマで決める。

## アプリドロワー

ドロワーは全アプリの一覧で、ホームとは独立した全画面である。
ドックの上スワイプで開き、検索欄と、ホームと同じ列数のグリッドを持つ。
アプリを長押しするとドラッグが始まり、ホームかドックの好きなセルに落とせる。

メイン画面のドロワーを 12 列にするか、左に検索と分類、右に一覧の 2 ペインにするかは決めていない。
カバー画面の 6 列で先に作り、メイン画面は実機で見てから決める。

## ドック

ドックはカバーとメインで共通の 1 本のレールにする。
One UI も両面で同じドックを出しており(docs/02)、ユーザーの現在の使い方と一致する。
置けるのは AppItem と FolderItem に限り、スロット数はテーマで決める。
ドックはドロワーを開くハンドルを兼ねる。

## 配置と見た目を別のファイルに分ける

docs/03 のテーマ JSON にはウィジェットの配置も含めていた。
これを、見た目を決める **テーマ** と、何をどこに置くかを決める **レイアウト** の二つに分ける。
配置はユーザーが日常的に変えるもので、テーマは滅多に変えないものだからである。
一つのファイルにしておくと、テーマを切り替えるたびに配置が巻き戻る。

- **テーマ**：配色、壁紙、装飾の有無、アイコン形状とラベルの有無(既定はラベルなし)、グリッドの寸法(列数とセルピッチ)、ウィジェット種別ごとのレンダラの選択、ドックのスロット数。既定レイアウトのプリセットを同梱してよい。
- **レイアウト**：カバー面のアイテム、拡張パネルのアイテム、ドックのアイテム。アンカーゾーンはカバー面への参照であり、独立したアイテムを持たない。

どちらも kotlinx.serialization で読み書きする JSON ファイルにし、アプリの内部ストレージに置く。
Room のようなデータベースは使わない。
アイテム数は多くても百数十で、構造が木であり、手で編集して書き戻せる利点のほうが大きい。
エクスポートとインポートを最初から付ける。

レイアウトは **LayoutRepository** が唯一の保持者になり、`StateFlow<Layout>` として画面に流す。
カバー画面とメイン画面のアンカーゾーンが同じ `Layout.cover` を読むだけで、docs/03 の「アンカー同期」が成立する。

## パッケージ構成

責務ごとに次のパッケージに分ける。

- `model`：Item の sealed 階層、Placement、Layout、Theme。
- `data`：LayoutRepository、ThemeRepository、AppRepository(v0.1 で作成済み)、LaunchLog、IconCache。
- `widget`：WidgetSpec、WidgetDataSource、WidgetRenderer、WidgetRegistry、各種別、AppWidget ホストの薄いラッパー。
- `ui`：カバー面、メイン面(アンカーと拡張)、ドック、ドロワー、フォルダポップアップ、編集モード。
- `theme`：テーマ JSON を Compose の値(色、形、フォント)に変換する層。

`ui` は `model` と `widget` のインタフェースにだけ依存し、ウィジェットの具体種別を知らない。

## マイルストーン

前回の中止の原因は作業量の見通しが立たなかったことなので、1 回のセッションで動く状態に到達する単位で区切る。

1. **アイテムモデルとレイアウト JSON**。Item と Layout を定義し、JSON から読んでカバー面のグリッドとドックに AppItem と手動 FolderItem を描く。初期配置は同梱のプリセット JSON で与える。
2. **ドロワーと編集モード**。全アプリ一覧と検索。長押しからのドラッグでホームとドックへ追加、移動、削除。アイコン同士を重ねてフォルダ作成。
3. **自作ウィジェット基盤**。三分割の枠組みとレジストリを作り、時計、計器、起動頻度グラフ、折りたたみメトリクスの 4 種別を載せる。ウィジェットのリサイズもここで入れる。
4. **規則つきフォルダ**。UsageStats の権限導線と、最近起動、よく使う、カテゴリの 3 規則。
5. **AppWidget ホスト**。バインドと設定アクティビティ、セル寸法の通知、ライフサイクル。
6. **メイン画面**。アンカーゾーンと拡張パネル。折りたたみ遷移の検証には実機か、正しく折りたためる AVD が要る。
7. **テーマ**。モックの 2 テーマを移植し、レンダラ切り替えと装飾を効かせる。

1 から 5 まではカバー画面だけで完結し、いまの AVD で動作確認できる。
