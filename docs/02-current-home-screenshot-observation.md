# 実機スクリーンショットからの観察(One UI 9 標準ホーム)

2026-08-21 にユーザーが撮影した実機スクリーンショット2枚(カバー画面・メイン画面、いずれも 13:05 撮影)からの観察をまとめる。
adb 実測の代わりにはならない項目もあるが、確定できたことと設計に効く発見が複数ある。

## スクリーンショットから確定できたこと

### 解像度とアスペクト比は公開スペックどおり

- カバー画面のスクリーンショットは縦長 10:16 で、ピクセル寸法は仕様値 1248 × 1972 と一致する。
- メイン画面のスクリーンショットはアスペクト比 1.325(≒4:3)で、仕様値 2448 × 1848(1.3247)と一致する(共有時に縮小されているが比率は保存されている)。
- **メイン画面はステータスバーが長辺上部に来る横向きで運用されている**。仕様書 01 の「メインは横長が一次状態」がユーザーの実運用でも裏付けられた。

### One UI 9 標準ホームの構造(カバー画面)

上から順に:

1. ステータスバー
2. ウィジェット行:Yahoo!天気(雨雲レーダー、約4×2)+ ピザ型天気ウィジェット(約2×2)
3. フォルダ行:フォルダ3つ(各フォルダは約2×2の大型表示で、中に最大9アイコンをグリッド表示)
4. アイコングリッド:**6列 × 3行**
5. ファインダー検索バー(全幅)
6. ドック:6アイコン(カメラ、Chrome、Gemini、WeatherNews、GitHub、Gmail)
7. ジェスチャーバー

カバーは幅74mmに6列。一般的なスマートフォン(4〜5列)より高密度で、10:16 の広い幅が実際に列数へ振られている。

**補足(ユーザー確認済み)**:One UI 標準のカバー画面グリッドは**4列が上限**で、この6列は Good Lock(Home Up)による拡張。
ユーザーは現在のサイズ感(セルピッチ 208px ≒ 12.3mm)を良好と感じており、**自作ランチャーでもこの密度を維持することが要件**。
つまり「標準ランチャーでは不可能な密度を Good Lock で無理やり実現している」状態であり、自作ランチャーが6列をネイティブにサポートすること自体が Good Lock 依存を1つ外す価値になる。

### One UI 9 標準ホームの構造(メイン画面)

- 全体は**約12列相当**の横長キャンバス。左右2つのゾーンに分かれて見える。
- **右半分はカバー画面のアイコングリッドとほぼ同一の配置**(Amazon, メルカリ, Bluesky, Notion, n, Kindle / Instagram, X, Discord, N, LINE / Threads, Facebook, Slack, ジャンプ+ ほか)。フォルダ3つも同一内容。
- **左半分はメイン画面専用の拡張ゾーン**:カレンダー、アラーム、ヘルスケア(消費カロリー・歩数・睡眠)、乗換、電話・メッセージ・ChatGPT・Teams などカバーに無いウィジェットとアイコン群。
- 検索バーとドック(6アイコン、カバーと同一)は下部中央に配置。
- 天気系ウィジェットはカバーとメインで別個体(表示気温も別:32°/29°)。

### タスクバー

どちらのスクリーンショットにも常駐タスクバーは写っていない(ジェスチャーバーのみ)。
非表示設定か自動非表示かは不明。仕様書 01 の「要検証」のままだが、少なくとも**常時表示では運用されていない**ことは確定。

## 設計に効く発見

### 発見1:One UI はカバーとメインで別レイアウトを持てる

仕様書 01 では「カバーとメインで別のホーム構造を持つこと」を差別化ポイントとしたが、スクリーンショットを見る限り One UI 9 は既にカバー用・メイン用の別レイアウトを保持している(ウィジェット構成が明確に異なる)。
差別化の主張はこう修正する必要がある:

- One UI のカバー/メイン分離は「ミラーリングするか、完全に別々か」の二択に近い。
- ユーザーは現に**右半分だけを手動でカバーと同期**させ、左半分を拡張ゾーンにしている。この「部分同期」を手作業で維持している状態こそが不満点=自作ランチャーの狙い目。

### 発見2:「メイン = カバー + 拡張パネル」という構造がユーザーの現実解

ユーザーの手動配置は「開くとカバーのホームがそのまま右側にあり、左側に広がった分の空間が足される」という心理モデルを示している。
これは Fold8 の物理形状(カバー幅74mm ≒ メイン長辺154mmの半分)と正確に対応する。
自作ランチャーの中核コンセプト候補:

> **カバー画面のホームをメイン画面の片側ゾーンとして自動で埋め込み(アンカー)、残り半分を「開いたときだけの拡張ゾーン」として別管理する。**

配置の同期を自動化すれば、ユーザーが今手作業でやっていることをそのまま製品化できる。
アンカーを左右どちらに置くか(利き手・持ち方)は設定項目にする。

### 発見3:カバー6列がグリッド設計の基準になる

カバーが6列で運用されているので、メインの拡張ゾーンも6列にすると「カバー1面 + 拡張1面 = 12列」で割り切れる。
セル幅はカバー実測で 1248px ÷ 6 = 208px/列。メイン側は 2448px ÷ 12 = 204px/列でほぼ同じ物理ピッチになり、**ppi 差(428 vs 404)を除けばアイコンの物理サイズをカバーとメインでほぼ一致させられる**。
これは仕様書 01 のウィジェット密度スケーリング問題への具体的な答えの土台になる。

## スクリーンショットでは確定できないこと(残る実測項目)

1. **densityDpi**(Size Class 分岐の決め手)。スクリーンショットは物理 px なので dp が出ない。
2. **カバーとメインが同一論理ディスプレイか別か**(ライフサイクル設計の決め手)。
3. **rotation 0 の基準**。
4. Jetpack WindowManager の FoldingFeature の返り値。

### adb を使わない代替手段

densityDpi だけなら adb 不要で確認できる:

- **設定 → 開発者向けオプション → 「最小幅」(Smallest width)** の数値を、折りたたんだ状態と開いた状態それぞれでスクリーンショットに撮る。これで `smallestScreenWidthDp` が直接読める。
- 同じく開発者向けオプションの「表示サイズ」を変えていないかも確認する(変えていると既定密度でない)。

1と3を完全に確定するには結局 adb が要るが、コマンドは仕様書 01 のブロックを折・開それぞれで1回ずつコピペ実行するだけでよい。
